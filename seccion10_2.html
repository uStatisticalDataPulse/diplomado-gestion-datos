Calidad como Código

Tradicionalmente, la calidad de datos se verifica después de que el pipeline termina (y el daño ya está hecho).
DLT invierte esto: Defines contratos de datos (Constraints) que se ejecutan fila por fila en tiempo real.

El Semáforo de Calidad

1. Warn

@expect

"Permite pasar el dato sucio, pero avísame". Ideal para monitorear tendencias sin interrumpir el negocio.

# Ejemplo: Email sospechoso @dlt.expect("email_valido", "email LIKE '%@%'")
Impacto: Solo Métricas

2. Drop

@expect_or_drop

"Si está sucio, tíralo". El dataset resultante queda limpio, pero pierdes volumen de datos. Estándar en capa Plata.

# Ejemplo: Precio negativo @dlt.expect_or_drop("precio_pos", "price > 0")
Impacto: Pérdida de Datos

¿Por qué es riesgoso?

Al usar drop, las filas desaparecen silenciosamente del flujo principal. Si tienes un error en la fuente que afecta al 50% de los datos (ej: cambio de formato de fecha), perderás la mitad de tu negocio sin que el pipeline falle.

Cálculo de Impacto
Entrada: 1,000,000 filas
Violaciones: - 50,000 filas (5%)
Salida Plata: 950,000 filas
Visualización del Filtro
graph LR Input[Datos] --> Filter{Valid?} Filter -- No --> Drop[🗑️ Papelera] Filter -- Yes --> Silver[Capa Plata] style Drop fill:#7c2d12,stroke:#f97316,stroke-width:2px style Silver fill:#064e3b,stroke:#10b981

3. Fail

@expect_or_fail

"Tolerancia Cero". Detiene todo el pipeline. Úsalo cuando un dato malo invalida todo el proceso.

# Ejemplo: ID Nulo @dlt.expect_or_fail("pk_not_null", "id IS NOT NULL")
Impacto: Parada de Producción

Implementación Multi-Regla

Rara vez usas una sola regla. DLT permite aplicar diccionarios enteros de reglas usando @dlt.expect_all....

quality_pipeline.py 
import dlt
from pyspark.sql.functions import *

# Definimos nuestras reglas de negocio en un diccionario
reglas_plata = {
    "valid_trans_id": "transaction_id IS NOT NULL",
    "valid_amount": "amount > 0 AND amount < 1000000",
    "valid_currency": "currency IN ('USD', 'EUR', 'COP')"
}

@dlt.table(
    name="silver_transactions",
    comment="Transacciones limpias listas para analítica"
)
# Aplicamos todas las reglas: Si falla CUALQUIERA, la fila se descarta
@dlt.expect_all_or_drop(reglas_plata)
def process_silver():
    return (
        dlt.readStream("bronze_transactions")
        .withColumn("processed_at", current_timestamp())
    )

El Patrón de Cuarentena

Cómo limpiar datos sin borrar evidencia.

Usar expect_or_drop es peligroso porque borras datos que podrían ser útiles o reparables. El patrón de Cuarentena divide el flujo: las filas buenas van a Plata, las malas van a una tabla de "Cuarentena" para auditoría. 

reglas = {"valid_score": "score >= 0 AND score <= 100"}

# 1. Tabla PRINCIPAL (Solo Datos Buenos)
@dlt.table(name="exam_scores_clean")
@dlt.expect_all_or_drop(reglas)
def scores_clean():
    return dlt.readStream("bronze_scores")

# 2. Tabla CUARENTENA (Solo Datos Malos)
@dlt.table(name="exam_scores_quarantine")
def scores_quarantine():
    return (
        dlt.readStream("bronze_scores")
        # Invertimos la lógica para capturar lo malo
        .filter("NOT (score >= 0 AND score <= 100)")
        .withColumn("reason", lit("Invalid Score Range"))
    )

Tip Pro: En la tabla de cuarentena, agrega siempre metadatos como ingest_date y file_source para ayudar al equipo de origen a corregir el error.
